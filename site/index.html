How it works

Five steps, and you can stop at any of them.

  1. Scan

    Lists your repositories and reads one file tree each. Read-only. Free.

  2. Audit

    Rule-based checks score every repo and produce a “fix these first” list. No model involved. Free.

  3. Generate

    Builds an evidence bundle per repo and asks Claude for a description, topics and a README.

  4. Review

    Every proposal is editable, side by side with the exact evidence the model was given.

  5. Apply

    Writes only what you approved. Dry run is on by default and prints the exact API calls without sending them.

The part that matters

Nothing is invented.

The failure mode worth caring about is a confident README describing features a project does not have. That is your name on the profile. Three things guard against it.

It only sees the evidence

The model is given the file tree, the real dependencies, the entry-point source and the commit history — and is instructed to describe nothing it cannot point at.

Output is schema-validated

Against GitHub's actual limits, before you ever see it: 350-character descriptions, three to six lowercase topics. Invalid output is rejected and retried, never surfaced.

It says what it did not know

Every proposal carries a confidence rating and lists what it could not determine. Repositories with too little code to describe honestly are skipped and reported, not padded.

From a real proposal — the unknowns field
“Whether the extension was ever published to the Raycast store — nothing in the repo says.”

Read the generated README before approving it. That is the step that makes this safe, and gitms is built so that step takes a minute rather than an afternoon.

The system prompt is identical for every repository in a run and marked as a cache breakpoint, so every request after the first reads it from cache. Mock mode runs the whole pipeline without calling the API — use it once before spending anything.

Safety

It is careful in the places where being wrong is expensive.

  • Only approved proposals are written. Never a pending one, never a skipped one, whatever the request asks for.
  • No silent overwrites. README commits pass the current file SHA, so a change made on GitHub since the scan fails cleanly with a 409. There is no force path.
  • Existing READMEs are backed up locally before being replaced, and applying is idempotent — an applied repo is skipped on re-runs.
  • Your keys stay on your machine. Held in memory by default and gone when the server stops. They are sent only to the Anthropic and GitHub APIs, never written into the project folder, never logged.
  • The server binds to loopback only, validates the request origin, and requires a per-process session token on every mutating request.

Install

Two commands, then two keys.

$npm install
$npm run dev

A browser opens at 127.0.0.1:5123. It asks for an Anthropic API key and a GitHub token with the repo scope, and tests both before letting you continue — testing the Anthropic key costs nothing, because it checks authentication without generating anything.
